# Automation

The organization owns the policy; this repository owns the adapters. Merge
decisions, dependency routing, version bumps, changelog commits, tags and GitHub
Release metadata are handled by **ThanhNguyxnAgent** from the central
[`ThanhNguyxnOrg/.github`](https://github.com/ThanhNguyxnOrg/.github) repository.
This repository keeps only what needs local knowledge: its test matrix, package
builds, the Store submission and two managed pull-request relay workflows. Code
scanning is GitHub's default CodeQL setup, configured in repository settings
rather than by a workflow in this tree.

## The control plane

The central repository holds the policies and the code that reads them:

| File | Purpose |
|---|---|
| `ci-policy.json` | The default branch and the exact required check names for every project, plus whether Dependabot may use guarded auto-merge. |
| `agent-policy.json` | Pull-request classification and routing rules. |
| `release-policy.json` | Version files, changelog path, release mode, build-workflow name and required assets per project. |
| `.github/workflows/agent-controller.yml` | Six-hour reconciliation, missed-event recovery and automatic onboarding of managed workflows. |
| `.github/workflows/release-controller.yml` | Conventional Commit classification, version/changelog commits, tags, draft releases and asset verification. |

The two files in this repository whose first line is

```text
# Managed by ThanhNguyxnAgent Auto-Onboarding. Do not edit this file manually.
```

are written by that onboarder. A local edit is overwritten on the next pass, and
a policy change belongs in the central repository instead.

## The agent identity

Every write performed by automation — labels, review routing, merges, onboarding
commits, tags, GitHub Releases — uses a short-lived installation token minted
from one GitHub App, so the pull request and the Release page record
**ThanhNguyxnAgent** as the actor rather than `github-actions[bot]`.

| | |
|---|---|
| App slug | `thanhnguyxnagent` |
| App ID | `4125740`, installed on the `ThanhNguyxnOrg` organisation |
| Organisation variable | `BOT_APP_ID` — the App's numeric ID, known without the private key, so it is not a secret |
| Organisation secret | `BOT_PRIVATE_KEY` — the only credential this repository forwards |
| Visibility | **Public repositories** only — see the warning below |
| Token mint | Central reusable workflows and the shared release publisher; this repository never mints one itself |

### The visibility trap

The organisation variable and the secret are scoped to *public repositories*.
This repository is public, so they resolve. **If the repository is ever made
private, they stop being visible to these workflows and every job that forwards
them fails.** The fix is to widen the visibility to include private repositories
(an organisation setting), not to add new secrets.

### Rotating the key

Generate a new private key in the App's settings, store it as `BOT_PRIVATE_KEY`
at the organisation level, and delete the old key. Nothing in this repository
changes, and no workflow edit is needed.

## Workflows

| Workflow | Trigger | What it does |
|---|---|---|
| `ci.yml` | Push to `master`, every pull request, manual | Delegates to the organization's `ci-node.yml`, pinned to a commit SHA. Runs the unit suite on Ubuntu (Node 22 and 24), Windows and macOS (Node 22), plus a `node --check` pass over every module. Read-only. |
| Code scanning | Pull requests and pushes, weekly; no local workflow | GitHub's default CodeQL setup runs the default query suite over the JavaScript and the Actions workflows, and uploads code-scanning alerts. It is configured in repository settings, so there is no `codeql.yml` to edit here. |
| `agent-pr-signal.yml` | `pull_request_target`; and `workflow_run` of the test workflows | Metadata-only. Writes a small JSON envelope with the repository, pull-request number and head SHA, then uploads it as a one-day artifact. No checkout, no secrets, no write token, no PR code. **Managed; do not edit.** |
| `agent-pr-worker.yml` | `workflow_run` after the signal completes | Forwards the signal artifact and `BOT_PRIVATE_KEY` to the central `agent-pr-worker.yml`. The central worker validates the event against the GitHub API and performs the actual routing or merge. **Managed; do not edit.** |
| `release.yml` | A tag is created; manual dispatch with an existing tag | The build adapter. Builds the six installers from the tag, verifies each bundle, launches the packaged app on its own platform, and uploads the assets to the tag's draft release through the shared publisher. It never creates a tag or a release. |
| `store.yml` | A stable Release is published; manual dispatch with an existing tag | Builds the Store package, checks the manifest identity and version against `store/identity.json` and the release tag, and submits the update to the Microsoft Store with the organisation's Partner Center credentials. A pre-release never triggers it. |

### The pull-request path

1. `agent-pr-signal.yml` runs from the base repository's default branch and
   records only GitHub-supplied metadata.
2. `agent-pr-worker.yml` runs in the privileged `workflow_run` context and passes
   that envelope to the central reusable worker.
3. The central worker checks that the pull request is still open and that its head
   SHA and head repository still match the event. It reads changed-file names,
   mergeability, checks and commit statuses through the API — it never checks out,
   downloads or executes pull-request code.
4. The central controller applies classification labels, holds risky changes for
   a person, and may enable guarded GitHub auto-merge for a low-risk Dependabot
   patch or minor update in an explicitly opted-in repository.

This repository has no local `auto-merge`, `merge` or `repo-setup` workflow. If
you find one, it is stale; delete it rather than fixing it.

### What is held for a person

| Change | Behaviour |
|---|---|
| Any change touching `main/**` or `preload.js` | `needs-review` and maintainer routing: the trust boundary is always read by a person. |
| A workflow or repository-automation change | `workflow-update` and `needs-review`, even when the diff is small. |
| A major, downgrade, unknown or security-sensitive dependency update | The matching dependency/security label and `needs-review`. |
| Failed, pending, missing, skipped or unconfigured required CI | `ci-failed`, `ci-pending` or `ci-missing`; the gate stays closed. |
| A merge conflict | `merge-conflict`; a person resolves it. |

Labels are routing metadata, not merge authorization. Unconfigured repositories
fail closed. A green unrelated check cannot substitute for a missing required
job.

The exact required checks for this repository are declared once, in the central
`ci-policy.json`:

```text
tests (ubuntu-latest, 22.x) / ubuntu-latest / node 22.x
tests (ubuntu-latest, 24.x) / ubuntu-latest / node 24.x
tests (windows-latest, 22.x) / windows-latest / node 22.x
tests (macos-latest, 22.x) / macos-latest / node 22.x
syntax / syntax check
```

The newest attempt for each exact name is authoritative, so a successful rerun
supersedes an older failure. Anything else — a missing check, a skipped or
neutral required check, a pending job — holds the pull request.

### The release path

`.github/workflows/release.yml` is only the build adapter. The central release
controller classifies Conventional Commits, writes the version files and the
changelog entry, commits the result as `release: vX.Y.Z`, creates the tag and a
draft GitHub Release, then waits for this repository's build to attach the
installers. It publishes the draft only after the build workflow succeeded for
the exact tag commit and every required asset in the central manifest exists.

See [RELEASING.md](RELEASING.md) for the person-facing procedure and the list of
required assets.

## Dependabot

`.github/dependabot.yml` is local because the ecosystem and the update groups are
project-specific. It opens npm updates weekly — minor and patch grouped into one
pull request, majors separate — and GitHub Actions updates weekly, grouped. It
requests no labels: classification and routing belong to the Agent.

The central `ci-policy.json` sets `autoMergeDependabot: true` for this
repository, so a Dependabot **patch or minor** update can enter the guarded
auto-merge path after every exact required check succeeds. A major, downgrade,
unknown or security-sensitive dependency update is routed to a person. So is
every non-Dependabot pull request, and every workflow change.

## Local build helpers

The scripts under `.github/scripts/` are used by the local workflows and tests:

| Script | Used by |
|---|---|
| `package-paths.mjs` | Resolves the packaged `app.asar` paths for the verification and smoke scripts. |
| `verify-package.mjs` | `release.yml`, `store.yml`: reads the packaged bundle and fails if the bridge, renderer entry point or runtime dependency is missing. |
| `smoke-package.mjs` | `release.yml`: starts the packaged app with a throwaway profile and library, then asks the page whether the bridge and editor came up. |
| `release-notes.mjs` | `tests/release-notes.test.mjs`: parses a `release: vX.Y.Z` subject and extracts a changelog section, so a manual release commit can be checked locally before it is pushed. |

## The App's permissions

The installation holds the permissions needed by the central control plane:

| Permission | Used for |
|---|---|
| Metadata: read | Enumerating the organisation's repositories during onboarding. |
| Contents: write | Onboarding commits, merges, tags and releases. |
| Workflows: write | Creating and updating the two managed workflow files. |
| Pull requests: write | Labels, review routing and merges. |
| Issues: write | The organisation's stale-lifecycle labels and comments. |
| Checks and commit statuses: read | Evaluating the exact required checks. |

This repository's own workflows request only `actions: read` and
`contents: read`; the shared publisher receives a repository-scoped token from
the central App. Reducing the installation's permissions is a central change and
should be checked against the central controllers first.

## Repository settings

Branch protection and rulesets can reject the onboarder's direct commits; those
failures are visible in the onboarding job rather than silently marking the
repository as enrolled. **Code scanning runs on the default setup.** A local
`codeql.yml` was removed on purpose: while it existed, the analysis job and the
default setup fought over the same alerts and every run failed with a conflict
error. Configure the languages and the schedule under "Code scanning" in
repository settings instead of adding the workflow back.

## Keeping this page honest

The names and rules here — App ID, secret names, workflow names, required checks
and managed-file policy — were read from the central repository and the workflows
in this one. If one of them changes, change this page in the same pull request. A
stale automation page is worse than none, because it is the page people trust
when a workflow fails.
